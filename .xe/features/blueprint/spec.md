# Feature: Stack Product Blueprint

## Problem

The legacy Stack (`~/dev/todo`) is PowerShell-driven and edited through PRs, so the task list is not reachable or editable from anywhere. Stack v2 must be a secure, $0-cost, accessible-anywhere task system that tells the owner what to do next and lets AI work the stack.

## Goals

- Tell the owner what to do next: scored, time-aware, across projects.
- AI works the stack: each task defines its autonomy level (triage, draft, execute; 🙋 human checkpoint).
- Capacity/planning per project and time block.
- Fast capture from any surface; recurring tasks roll automatically.
- Reachable from anywhere (web desktop + mobile, CLI, REST, MCP, chat bots) with no PR workflow.
- Editing in the UI is easier than editing text, so text is never required.
- Built for the owner first; shippable as Xerilium Stack; later a feature of Xe Prime.

Explicit non-goals:

- Multi-user/teams in v1 (design must not block it).
- Migrating or modifying `~/dev/todo` data (agents never touch it; owner cuts over by choice).
- Merging PRs or deploying to production by agents.

## Scenario

- As the owner, I need a single "next task" answer so that I stop deciding what to work on.
  - Outcome: top task matches legacy ranking on real data (golden parity).
- As the owner on a phone, I need touch/speech capture and pickers so that adding or updating a task takes seconds without typing emojis.
  - Outcome: add + set metadata in ≤3 taps plus speech or a short phrase.
- As the owner on desktop, I need keyboard-first control and a command palette so that start/complete/skip never need the mouse.
  - Outcome: every lifecycle action has a shortcut and palette entry.
- As an agent, I need a token-efficient API/MCP so that I can read the next task, add, triage, and complete within my autonomy limit.
  - Outcome: "next" response ≤ 300 tokens; all core flows available over MCP.
- As the owner, I need my task list never to leak so that I can host it publicly reachable.
  - Outcome: every unauthenticated request is denied; security tests pass.
- As the owner, I need recurring tasks to roll on their own so that admin chores never need re-entry.
  - Outcome: completing a 🔄 row advances its date per cadence.

## Success Criteria (acceptance criteria; all must be true)

1. **Parity:** scoring, summaries, and lifecycle outputs match legacy golden outputs on a copy of the owner's real tasks.
2. **Round-trip:** every legacy `tasks/*.md` parses and re-serializes byte-exact via the emoji formatter.
3. **Tests:** unit and browser e2e green in CI; core line coverage ≥ 90%; tests written before implementation per slice.
4. **Security:** threat model and checklist pass; unauthenticated requests return 401/redirect on every route; tokens scoped, revocable, hashed; no task data in client bundle or logs; verified by tests.
5. **Surfaces:** web (desktop keyboard + mobile touch/speech), CLI, REST, MCP, and bot hook all complete next/add/start/complete/skip/resume/set-properties.
6. **No PRs:** a web edit lands as a direct commit in the data repo within seconds.
7. **Cost:** runs within free tiers, documented.
8. **Traceability:** every requirement maps spec → test → code in `.xe`.
9. **Docs:** README, API/MCP reference, deploy runbook usable cold.
10. **Scoring bake-off:** report delivered; default engine unchanged unless the owner approves.

## Design principles

- **Make the UI beat the text**
  > Pickers, shortcuts, and natural-language capture must be faster than typing emojis; the markdown remains an escape hatch.
- **Keep markdown the truth, behind an interface**
  > Storage and format are adapters. Markdown in a private git repo is first; format-neutral internal model; DB/API adapters later.
- **Default to deny**
  > No route, token, or log exposes task data unless explicitly authorized.
- **Prove parity before changing behavior**
  > Legacy output is the contract; redesigns ship behind configuration and a bake-off.
- **Favor reversibility**
  > Direct commits are fine because git history makes every change revertable; agents never merge or deploy.
- **Spend tokens only where they matter**
  > API/MCP responses are terse and structured.

## Requirements

### Functional Requirements

- FR1 Task model: format-neutral internal model with status, priority, impact, effort, value, dates, recurrence, autonomy level, subtasks, notes, projects, sections, capacity, time blocks.
- FR2 Formatters: pluggable; emoji-markdown (legacy, lossless in-place edit) and clean (YAML/structured); either selectable per repo; dual output supported.
- FR3 Recurring: daily/weekly/monthly/quarterly/yearly, weekday names, `Quarterly-EOM+1`; both legacy and canonical row forms; roll in place on complete; subtasks reset; month-end clamp; weekend shift to Monday (config, default on) without drift (nominal day retained).
- FR4 Config: legacy `.xe/config/stack.json` shape/path honored with baked-in defaults.
- FR5 Scoring: pluggable engine; default = legacy `(weights + project value + placement) / effort hours`; time-block filtering (🚨 bypass, ☀️ work only); golden-tested.
- FR6 Lifecycle: start, complete, skip/park, resume, suspend, set-properties, remove-completed, add-project, add-task; ⏰ start-date and 💤 suspend sweeps.
- FR7 Summaries: README, stack, projects, my-day.
- FR8 Storage: git adapter via GitHub API/local git, direct commits, atomic writes, conflict-safe.
- FR9 API: REST over the core; MCP server; webhooks; GitHub Actions hooks.
- FR10 Web app: next-task view + actions, quick capture (NLP + speech), full list/filters/capacity view, inline markdown editor, drag/reorder + bulk edit, command palette, mobile touch UX.
- FR11 CLI: init, add-project, add, next, start, complete, skip, resume, suspend, set, remove-completed, update.
- FR12 Query tasks: 🔎 GitHub-sourced generated subtasks (🌐 prefix), failure leaves existing list untouched.
- FR13 AI: triage (🪄/🙋 subtasks), assist (execute within the task's autonomy level, results logged), chat bots (iMessage/Slack).
- FR14 Scoring bake-off: separate redesigned engine evaluated against default on real data.

### Non-functional requirements

- Cost: $0 on free tiers (Azure Static Web Apps + managed Functions; secrets in SWA app settings, not Key Vault).
- Security: SWA built-in auth (GitHub/Entra) allow-listed to the owner; hashed, scoped, revocable API tokens; threat model; deny by default.
- Reliability: git is the durable store; writes atomic; retries on conflict.
- Performance: next-task API p95 < 500 ms warm; web interactive < 2 s on mobile.
- Observability: audit via git history; structured logs without task content.
- Accessibility: keyboard complete; WCAG AA contrast; screen-reader labels.
- Globalization: ISO dates internally; locale-aware display.
- Backward compatibility: legacy format loads and round-trips byte-exact.
